AIE3 — Клиент для эмбеддинг-API
Описание

Проект реализует клиент для mock Embedding API с обработкой ошибок и повторными запросами.

Основные задачи проекта:

создать mock API, возвращающий embedding;
реализовать клиент с повторными запросами при временных ошибках;
различать временные и постоянные ошибки;
использовать экспоненциальную задержку между попытками;
написать тесты без реальных сетевых запросов;
сравнить разные стратегии retry в benchmark.

Mock Embedding API

Файл: src/mock_embedding_api.py

Mock API имитирует работу сервиса эмбеддингов.

Endpoint:

POST /embed

В запрос передаётся текст:

{
  "text": "Привет"
}

При успешном запросе API возвращает JSON с embedding:

{
  "embedding": [0.123, -0.456, 0.789]
}

Embedding содержит 128 чисел с плавающей точкой. Размер 128 задан условиями проекта.

Для генерации значений используется random.uniform(-1, 1).

Запуск API

Из корня проекта:

uvicorn src.mock_embedding_api:app --reload

После запуска API доступен по адресу:

http://127.0.0.1:8000

Документация Swagger:

http://127.0.0.1:8000/docs

Через Swagger можно отправить POST-запрос на /embed и проверить ответ сервера.

Embedding Client

Файл: src/embedding_client.py

Основная функция клиента:

get_embedding(text, retry_config)

Она отправляет текст на Embedding API и возвращает полученный список чисел.

Пример конфигурации:

retry_config = {
    "max_retries": 3,
    "initial_delay": 1,
    "multiplier": 2
}
Retry-логика

Клиент повторяет запрос, если произошла временная ошибка.

Временные ошибки:

Ошибка	Причина
429	слишком много запросов
500	внутренняя ошибка сервера
503	сервис временно недоступен
Timeout	сервер не ответил вовремя

Постоянные ошибки:

Ошибка	Причина
400	неправильный запрос
404	ресурс не найден

При постоянной ошибке повторять запрос бессмысленно, поэтому клиент сразу завершает работу с ошибкой.

Экспоненциальная задержка

Между повторными запросами используется экспоненциальная задержка.

При параметрах:

initial_delay = 1
multiplier = 2

задержки будут:

1 → 2 → 4 секунды

Если:

max_retries = 3

это означает 3 повторные попытки после первоначального запроса.

Таким образом, максимальное количество HTTP-запросов:

1 первоначальный запрос + 3 повторные попытки = 4 запроса

Такой подход позволяет дать временно недоступному сервису возможность восстановиться, но одновременно ограничивает количество повторов.

Ошибки и информация о повторных попытках выводятся в stderr.

### Обоснование параметров retry

По умолчанию используются следующие параметры:

- `max_retries = 3` — три повторные попытки после первоначального запроса. Это ограничивает количество обращений к API и позволяет восстановиться после временных сбоев.
- `initial_delay = 1` — начальная задержка в одну секунду. Она позволяет не повторять запрос мгновенно после ошибки.
- `multiplier = 2` — удваивает задержку после каждой неудачной попытки. Получается последовательность 1, 2 и 4 секунды.

Эти значения выбраны как компромисс между надёжностью, временем ожидания и нагрузкой на API. Для конкретного сервиса параметры можно менять в зависимости от частоты сбоев и требований к скорости ответа. Если каждый запрос платный, увеличение числа повторов также увеличивает расходы, поэтому стратегию следует выбирать с учётом стоимости запросов.

Тестирование

Файл: src/test_embedding_client.py

Для тестирования используется pytest.

Тесты не выполняют реальные HTTP-запросы. Вместо этого используется unittest.mock, который заменяет requests.post на mock-объект.

Это делает тесты:

быстрыми;
предсказуемыми;
независимыми от состояния API;
безопасными для запуска без работающего сервера.
Проверяемые сценарии

В тестах проверяются следующие ситуации:

успешный запрос;
временная ошибка 500, после которой запрос становится успешным;
постоянная ошибка 404;
Timeout с последующим успешным запросом;
max_retries = 0;
исчерпание всех повторных попыток.

Для временных ошибок проверяется количество вызовов mock-запроса через:

mock_post.call_count

Например, если первый запрос получил 500, а второй оказался успешным, ожидается:

call_count = 2
Запуск тестов

Из корня проекта:

pytest src/test_embedding_client.py

Текущий результат:

6 passed
Benchmark

Файл: src/benchmark_retries.py

Benchmark сравнивает несколько стратегий обработки временных ошибок:

No retry — запрос выполняется только один раз;
Manual retry — повторные попытки реализованы вручную;
Tenacity — retry реализован с помощью библиотеки tenacity.

Для сравнения используются 100 одинаковых сценариев запросов.

В benchmark проверяются разные значения max_retries:

0;
1;
3.
Результаты

Один из запусков benchmark:

Method	Successful	Failed	Time
No retry	70	30	0.0000 sec
Manual retry (0)	70	30	0.0000 sec
Manual retry (1)	92	8	0.0542 sec
Manual retry (3)	99	1	0.0876 sec
Tenacity (1)	92	8	0.0619 sec
Tenacity (3)	99	1	0.0930 sec

Результаты зависят от случайно сгенерированных сценариев, поэтому при повторном запуске значения могут немного отличаться.

Анализ

Без retry успешными оказываются только запросы, которые проходят с первой попытки.

Увеличение количества повторных попыток повышает надёжность:

max_retries = 1 позволяет восстановить часть неудачных запросов;
max_retries = 3 обеспечивает ещё более высокий процент успешных запросов.

При этом дополнительные попытки увеличивают время выполнения.

Manual retry и Tenacity показывают практически одинаковый результат по успешным запросам. Manual retry даёт полный контроль над логикой и не требует дополнительной библиотеки, поэтому именно этот подход используется в основном клиенте.

Tenacity удобен тем, что позволяет компактно описать retry-логику, но в основном клиенте он не используется, так как по условиям проекта retry необходимо реализовать самостоятельно.

Почему не стоит бесконечно повторять запросы

Повторные запросы повышают вероятность успеха, но одновременно увеличивают:

время ожидания;
количество HTTP-запросов;
стоимость использования API.

Например, если один API-запрос стоит $0.001, большое количество повторных запросов увеличивает итоговую стоимость.

Поэтому max_retries = 3 является компромиссом между надёжностью, временем ожидания и количеством запросов.
